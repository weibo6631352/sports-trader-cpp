## 0. TL;DR

我们公司没有 retail 用户, "用户" = 操作员 + 量化研究员 + 风控员 + 值班 SRE. 他们一天会盯 8~12h 屏, 看 CLI / Grafana / 日志 / 告警 / YAML config / 内部 web. **UX 在这里不是"好看", 而是"不让人在凌晨 3 点 NBA 末节关键球时按错按钮"**.

本框架定义:

1. 7 个 UX 维度 (信息密度 / 阅读路径 / 错误可读性 / 报警噪音 / 决策延迟 / 心流 / 切换成本)
2. 每维 1-10 评分卡 + 准入卡阈值 (低于阈值禁止上线)
3. 报警 subject / body / 严重度 标准
4. 错误信息双层 (操作员可读 + 工程师可调) + 错误码 5 段编码
5. Dashboard 一屏纪律 + 颜色 4 色法
6. UX 周报三段式模板
7. 跨 agent prompt 沟通体感 checklist
8. 给小苏 / 小郑的具体 backlog
9. 我接下来要 dogfood 的清单

**最关键的一维: 报警噪音 (alert noise).** 这是凌晨 3 点把操作员叫醒的那一下, 一旦失控, 整个团队会进入"狼来了"模式, 真出事时反而没人理. 这一维 < 7 分一票否决.

## 1. 用户画像与一天 (Persona × Day in the Life)

我们必须先把"谁在用"说清楚, 否则后面所有维度都是空谈.

### 1.1 三类内部"用户"

| 用户 | 一天主要动作 | 主要界面 | 最怕什么 |
|---|---|---|---|
| **操作员 (trader on duty)** | 盯赛 + 看持仓 + 看异常 + 偶尔手动干预 (kill switch / 暂停某市场) | Grafana 主盘 + CLI `pmctl` + 告警 (PagerDuty/IM) | 漏报警 / 错按 kill / 信息淹没 |
| **量化研究员 (小程/小蒋/小袁)** | 看回测 + 改策略 YAML + 看实盘 vs 回测 diff | Jupyter / CLI 回测器 / Grafana 策略页 | 数字看不懂 / 回测实盘对不上 / YAML 改错 |
| **风控员 (老韩/老沈/老唐)** | 看 limit / 拒单率 / audit / 异常持仓 | 风控 dashboard + audit 流 + 告警 | 拒单原因不清 / 风控触发但没记录 / audit 缺字段 |

**一天典型节奏 (以操作员视角):**

- **08:30** — 接班. 先扫一眼"昨日复盘卡片"+ "未处理告警". 期望 5 分钟内进入状态.
- **10:00** — daily standup, 切到 IM. 期望 standup 时还能瞄到主盘 (单屏可见 / 不要切窗口).
- **12:00-18:00** — NBA / MLB inplay 高峰. 注意力主要在 Grafana 主盘 + 告警声. 期望"无事时屏幕安静".
- **凌晨 02:00-05:00** — 美西黄金时间, 跨洋链路最不稳的时候. 期望"告警准, 误报 ≤ 1/晚".
- **每周五 16:00** — retro. 期望日志能快速 grep 出"本周拒单 top 10 原因".

> 这套时间线就是评估所有维度的底层尺子. 任何 UI / 告警 / CLI, 想象操作员在凌晨 3 点眯着眼用它, 通不通?

## 2. UX 七维定义 (Dimensions)

| # | 维度 | 通俗说 | 量化口径 (从哪测) |
|---|---|---|---|
| D1 | **信息密度 (info density)** | 一屏装多少东西不挤不饿 | 主盘一屏 widget 数 / 字段数 / 是否有滚动 |
| D2 | **阅读路径 (reading path)** | 眼睛从左上角走到关键数字要几跳 | F-pattern 测试 + 操作员视频回放跳数 |
| D3 | **错误可读性 (error readability)** | 报错是不是"人话" + 给不给"下一步" | 抽样 50 条 error, 操作员盲读, 看懂率 |
| D4 | **报警噪音 (alert noise)** | 半夜被叫醒值不值 | 每周 alert 数 / 真阳率 / MTTAck |
| D5 | **决策延迟 (decision latency)** | 看到→理解→动作的时间 | 端到端 stopwatch (UI render + 人眼 + 手) |
| D6 | **心流 (flow)** | 1h 内被打断几次 / 注意力是否散 | 自评 + 操作员 1:1 |
| D7 | **切换成本 (context switching)** | 在 CLI/Grafana/IM/日志之间跳几次 | 一次"处理一个事件"的窗口切换次数 |

每个维度都给 0-10 分, 评分卡见 §3.

### 2.1 维度细则

#### D1 信息密度

- 太挤 (>30 个数字塞一屏): 累, 错读
- 太空 (<5 个有效数字): 操作员要切窗口看其他信息, 切换成本上升 (拖累 D7)
- **甜区:** 主盘一屏 12-18 个核心数字 + 3-5 个图, 字号不小于 14px, 不需要横向滚动

#### D2 阅读路径

- "我最该看的数字"必须在左上角 1/3 屏内, 或在屏幕中央偏上 (符合 F-pattern + 中心视觉)
- 不能要求操作员"先看 A 再算 B 才能判断 C", 派生数字应该提前算好显示
- 颜色 / 字号 / 加粗 是路径权重的体现, 不要乱用

#### D3 错误可读性

每条 error 必须满足"三件套":

1. **是什么** (人话, 不是 stack trace 头)
2. **影响什么** (要不要紧, 哪些下游受影响)
3. **下一步做什么** (确定动作或"去问谁")

反例: `Error: ECONNRESET at line 2341 in client.cpp`
正例: `[NET-E0042] Polymarket WSS 连接被对端重置. 影响: NBA 主盘价格 5s 内不更新; 系统会自动重连. 操作员: 观察 30s; 若超时未恢复 → ./pmctl wss-reset.`

#### D4 报警噪音

- 真阳率 (TP rate) ≥ 80% — 10 条响 8 条该响
- 每周 P1+ 数 ≤ 20 条 (操作员 / 值班体感不被淹)
- MTTAck (mean time to ack) ≤ 5min — 操作员看见即响应
- **静默时长** (没事的时候应该静音): 99% 工作时间无 P0/P1 告警

#### D5 决策延迟

参考老姜 @ S1-011 拆解 (决策内环 < 500us), 但 UX 决策延迟说的是**人的部分**, 不是机器:

- 信息上屏 → 操作员理解 → 操作员动作, 目标 p95 ≤ 3s (kill switch 类)
- 一般 "看一眼判断要不要紧" 应 ≤ 1s

**注:** 机器决策延迟 (订单链路) @老姜 已 own, 我不重复. 我管的是"人在闭环中的延迟".

#### D6 心流

- 操作员主观打分: 一天结束累不累 (1-10)
- 60 min 内的非必要打断次数 ≤ 1
- "切了一下 IM 回来要不要 30s 才找回上下文" — 不要 (说明 D2/D1 没做好)

#### D7 切换成本

处理一次告警/异常, 期望窗口切换 ≤ 3 次 (Grafana → CLI → 日志). 切到第 4 个窗口说明工具没合好.

### 3.2 准入卡阈值 (Gate)

| 类型 | 阈值 |
|---|---|
| **任何单维 < 5** | 一票驳回, 必须改 |
| **D4 报警噪音 < 7** | 一票驳回 (这一维特别严, 因为是 24h on-call 体验) |
| **D3 错误可读性 < 6** | 不能上 P0 路径 (订单 / 风控 / 资金) |
| **平均 ≥ 7** | 标准通过 |
| **平均 6-7** | 有条件通过 + 1 sprint 内补改 |
| **平均 < 6** | 整体驳回 |

> 准入卡只对"操作员看得到的东西"生效. 内部库函数不走 UX 评审.

## 4. 报警可读性标准 (Alert Standard)

### 4.1 严重度分级

| 级别 | 定义 | 响应 SLA | 通知方式 | 例 |
|---|---|---|---|---|
| **P0** | 资金 / 风控失效 / 系统全停 | 立即, 电话 + IM + 短信 | 三路冗余 | RiskManager 被绕过 |
| **P1** | 单市场不可下单 / 数据源全断 | ≤ 5 min | IM + 桌面 | Polymarket WSS 全断 30s |
| **P2** | 单赛事数据延迟 / 单策略未运行 | ≤ 30 min | IM | Goalserve 单赛事 push 卡 5s |
| **P3** | 长期趋势异常 / 容量预警 | 工作时间 | dashboard 角标 | 磁盘 75% |
| **P4** | info / 复盘提示 | 不打扰 | 日志 / 周报 | "今日成交 1234 单" |

**红线:** P0 / P1 必须能被一句 IM 概括读懂, 不需要点开链接才知道是什么.

### 4.2 报警 subject 模板 (强制)

```
[<P级>][<模块>][<sport?>] <一句话症状>  (持续 <时长>)
```

例:
- `[P0][Risk][-] RiskManager 心跳超时 12s — 下单链路即将冻结`
- `[P1][Polymarket-WSS][NBA] 主盘 WSS 断连 30s — 触发自动重连第 2 次`
- `[P2][Goalserve][MLB] inplay push 滞后 5s — 单赛事 ID 7788`

### 4.3 报警 body 必含字段

```
- 现象: <什么不对>
- 影响: <哪些市场/赛事/策略/资金 受影响, 量化>
- 自动动作: <系统已经做了什么>
- 人工建议: <要不要操作员动手, 怎么动>
- 相关链接: <Grafana panel + runbook + audit 查询>
- 触发规则 ID: <ALERT-XXXX>
- 触发时间 + 持续: <ts + duration>
```

缺一不准上线. 由 @小郑 (observability) 在 alertmanager 模板里强约束.

### 4.4 报警生命周期

- **触发** → 必须 5min 内被 ack (否则升级)
- **静默** (silence) → 必须带 reason + expire, 不许永久 silence
- **关闭** → 必须有 resolution 备注 (一句话)

## 5. 错误信息标准 (Error Message Standard)

### 5.1 双层错误 (双轨制)

每个 error 必有两个面:

- **operator face (操作员可读)**: 中文 + 短句 + 下一步, 走 UI / 告警 / IM
- **engineer face (工程师可调)**: 英文 + stack + 上下文 (req_id / trace_id / market_id) + 时间戳, 走日志

不能只有一个. 只有 stack trace 的 error 视为"未完成".

### 5.2 错误码 5 段编码

```
[<DOMAIN>-<SEVERITY><NNNN>]
```

- `DOMAIN`: 3-4 大写字母, e.g. `NET` / `RISK` / `POLY` / `GOAL` / `ORD` / `CFG` / `KEY` / `DATA`
- `SEVERITY`: 1 个字母: `F` (fatal) / `E` (error) / `W` (warn) / `I` (info)
- `NNNN`: 4 位数字, 同 domain 内唯一, 0001 起

例:
- `[RISK-F0001]` 风控失效, fatal
- `[POLY-E0042]` Polymarket WSS 错误第 42 号
- `[CFG-W0007]` YAML 配置加载时某字段被默认值替换

错误码全表由小尤维护到 `docs/RESEARCH/xiaoyou-error-code-table.md` (下个 sprint 启动).

### 5.3 错误"下一步"必填

每条 error 必带 `next_action`, 4 选 1:

1. `auto` — 系统会自己解决, 操作员观望 (附时间预估)
2. `wait` — 等下游恢复, 不要乱动
3. `manual:<cmd>` — 执行某 CLI, e.g. `manual:./pmctl wss-reset --market nba`
4. `escalate:<who>` — 找谁, e.g. `escalate:老韩` (风控员)

### 5.4 反例 / 正例对照

反例 (现在多数语言默认错):
```
terminate called after throwing 'std::runtime_error' what(): connection lost
```

正例 (符合标准):
```
[POLY-E0042] Polymarket WSS 连接丢失
  现象: NBA 主盘 WSS endpoint 在 02:14:33 UTC 断开
  影响: 4 个 NBA 在售市场 5s 内价格不更新; 已暂停下单 (RiskManager 自动)
  自动动作: 第 1 次重连进行中, 预计 3s 完成
  操作员: auto (等待 ≤ 10s); 若 10s 未恢复 → manual: ./pmctl wss-reset --src polymarket
  trace_id: 9f3a...    req_id: 7788
```

## 6. Dashboard 设计准则

### 6.1 一屏信息量 (One-Screen Rule)

操作员主盘必须满足:

- **不滚动** — 1080p / 1440p 标准屏一屏装完
- **12-18 个核心数字** (PnL / 持仓 / 拒单率 / 延迟 p99 / WSS 心跳 / 主源在线 / 风控 limit 用量 / 当日成交数 ...)
- **3-5 张小图** (PnL 曲线 / 延迟分布 / 拒单趋势)
- **左上角 = 最该看的**: "现在系统正不正常 + 现在能不能下单"

### 6.2 颜色 4 色纪律

只用 4 种语义色, 不要彩虹:

| 颜色 | 含义 | 使用场景 |
|---|---|---|
| **绿** | 正常 / on | 心跳 ok / 在售 / 阈值内 |
| **黄** | 注意但不紧急 | 接近阈值 / 重试中 / 延迟抖动 |
| **红** | 异常, 要看 | 阈值越界 / 断连 / 风控触发 |
| **灰** | 未启用 / 无数据 | 模块关闭 / 数据缺失 |

**禁:** 蓝 (会和默认链接色混) / 紫 / 橙 / 粉. 单一 dashboard 颜色种类 ≤ 5 (含中性的黑白灰).

### 6.3 颜色不可单独承载信息

色盲友好 + 截屏到 IM 不丢信息: 颜色 + 文字标签 + 图标, 三件套.

### 6.4 数字纪律

- **百分比** 一律小数点后 1 位 (`12.3%`), 不要 `12.34567%`
- **延迟** 单位明示 (`us` / `ms` / `s`), 大于 1000 自动换单位
- **金额** 带货币 + 千分位 (`USDC 12,345.67`)
- **空值** 显示 `—`, 不显示 `null` / `undefined`

### 6.5 闪烁 / 动画纪律

- 仅 P0 / P1 告警 widget 可闪烁
- 闪烁频率 ≤ 1 Hz (不能像广告牌)
- 不许全屏背景闪 (操作员一晚要看 8h)

## 8. 跨 Agent 沟通体验 (Inter-Agent UX)

我们是 50+ agent 班子, agent 之间互相 prompt / 拉对方做事 也是"用户体验". 公司价值观第 4 条 **不耻下问** 要变成 UX 而不是口号.

### 8.1 cross-agent prompt 体感 checklist

任何 agent 拉另一个 agent 时, prompt 应满足:

1. **称呼到位** — "小郑你能不能..." 而不是 "observability-engineer pls"
2. **上下文齐** — 给 ticket 号 + 现状 + 你已经试过什么
3. **问题闭合** — 问"我该选 A 还是 B (附理由)" 而不是"你怎么看"
4. **边界尊重** — 不让对方做他声明里"拒接"的事
5. **回路明确** — "答完请回到我 (或 @ 老胡)"

不达标的 prompt → "沟通体验差", 计入跨 agent UX 月报.

### 8.2 跨 agent 求助"不耻下问"是否顺畅 — 测量口径

- **求助响应中位时长** (问到答完): 目标 ≤ 30 min (同 sprint 内)
- **来回轮次** (clarification round): 目标 ≤ 2 轮
- **拒接率** (合理拒接 / 总求助): 期望 5-15% (太低说明大家越界接, 太高说明边界不清)

### 8.3 跨 agent 沟通反例

反例: "老韩, 风控的 code 给我看下." — 称呼对但上下文缺失, 老韩不知道你要看哪一段.

正例: "老韩, S1-022 我要写'人为决策延迟'阈值. 你这边 RiskManager 在 P0 拒单时, **操作员侧人为应对时间窗** 你期望多长? 我倾向 3s, 想求证. 答完请回到我."
