## 0. 一句话结论

本会话是 §10.2 新模式 (GM 写码 + 全员评审) 的**首次满负荷压测, 结果正向**: 「派专家出 spec → 签字 → GM 实现 → 全量测试 → 双签 → push」闭环跑通 6 个 P0/子项, **至少抓出 2 个真 bug (单位冲突 + PnL 1e6 bug)**, 证明 spec+双签对**契约级/风控级改动 ROI 极高**。代价是**节奏不可持续** (一天 11 核心 commit + 近 10 专家召唤) 且**部分小改动也吃了重流程**。四个 MVP 验收项里**「第一笔成交」「零风控失效」推进显著但都未达 M1 demo 线**, 卡点不在代码而在 **Goalserve 白名单 (外部 blocker)**。

### 1.2 流程效率评估

**高效之处:**
- **关卡1 (spec 前置) + 关卡2 (改 RM 复签) 双闸**真拦住了风险。P0-1 老周在 spec 阶段就抓出老韩「零换算直搬」误判 (whole vs micro 差 1e6), **bug 死在编码前**, 这是 spec 最高价值的一次兑现。
- **实施→补 spec 回路顺畅**: P0-1 GM 实施时挖出 PublishLedgerSnapshot PnL 1e6 bug, 没硬扛, 当场登记 backlog + deferred DD 喂数, 决策链没断。
- **CI grep 哨兵 (⑧)** 把「单位契约」从「靠人记」变「靠门禁」, 是本会话最值钱的流程沉淀 (见 §5 SOP-1)。

**瓶颈:**
1. **GM 是唯一写码 throughput, 串行成颈**。6 个 P0 子项全过 GM 一支笔, 专家只能等 GM 实现完才能复签 → 专家 idle + GM 满载。这是 §10.2 模式的结构性单点。
2. **复签往返延迟**: 改 RM 必老韩复签 (关卡2), 老韩一天被拉 ≥4 次, 每次 context 重载。改动密集时复签成 GM 等待点。
3. **小改动吃重流程**: P0-3 (enable_paper_fills 默认 false + 加开关) 是「小改、安全默认、即时可做」, 但仍走了审查会登记 + GM 拍板路径。安全默认翻转这类**单向安全**改动不该和契约级改动同规格 (见 §3 过度流程)。

## 3. spec+双签的 ROI

### 3.1 抓出的真 bug (兑现价值)

| # | bug | 谁抓 | 阶段 | 后果(若漏) |
|---|---|---|---|---|
| 1 | **单位冲突 whole pUSD vs micro 差 1e6** | 老周(spec阶段) | 编码前 | exposure 红线静默架空, 实盘资金量级错 |
| 2 | **PublishLedgerSnapshot PnL 1e6 bug** | GM(实施时) | 编码中 | unrealized PnL 错 1e6, DD 熔断喂错数 |
| 3 | **fee 门 sizing/RM 用不同 p** | 小袁(c3副产物) | 测试激活后 | 极小 edge 下 sizing 显正 RM 拒, 37/9863 |
| 4 | **测试时间戳 stale>1yr 假绿** | c3 实施暴露 | 测试层 | Test1/4/6 evaluate 路径长期空过 (测试质量洞) |

**4 个真问题, 2 个在「编码前/编码中」被 spec+评审拦下**, 这是 spec 流程的核心 ROI: 风控级/契约级 bug 一旦进 main 再炸成本是数量级的 (单位 bug 可静默烧钱)。bug #4 还顺带暴露测试假绿债, 是评审的额外收益。

### 3.2 ROI 判定: 分层

- **契约级/风控级改动 (P0-1/P0-2/P0-6): spec+双签 ROI 极高, 必保留。** 这类改动单位/边界一错就静默烧钱或架空红线, 编译器不报、测试可能假绿, 唯一防线是人评审 + CI grep。
- **单向安全改动 (P0-3 默认 false / P2-1 fail-closed): 重流程是过度。** 这类改动方向单调安全 (从开火→默认关、从模糊→拒), 最坏结果是「过于保守少成交」不是「烧钱」, 不该和契约级同规格走审查会+拍板。建议降级为「GM 直接做 + 周报追认」(SOP-3)。

**结论: spec+双签值, 但要分层施加。** 本会话的过度流程主要在 P0-3 这类单向安全项陪跑了重流程, 占用了审查会与拍板带宽。

## 6. 节奏可持续性

**强度画像:** 一天内 = 开发线 11 核心 commit (6 个 P0 子项全闭环) + 部署线伦敦 EC2 从零到实连 + 召唤近 10 专家(老郭/老韩×4/老周/老高/小袁/小梁/老姜)。

**不可持续点:**
1. **GM 单点写码 throughput** (§10.2 结构性单点): MVP 攻坚期特例可短冲, 但所有 P0 串行过一支笔, 专家复签往返成等待。**建议: 单向安全/卫生类(P2)放给 IC, GM 只保契约/风控/架构敏感的写码**, 降单点负载。
2. **专家复签密集 context 重载**: 老韩一天被拉 ≥4 次。**建议: 同批改动攒一次复签 (如 P0-2 c2/c3/c5 可一次性 RM 复核), 减往返。**
3. **双线并行注意力切换**: 开发线与部署线共享 gcc 移植 bug 修复(b3b6d4c/f4be5b5)是好的协同点, 但两线 context 切换有隐性成本。**建议: 部署线非阻塞时段批处理, 不与开发线 P0 关卡交错。**

**可持续性判定: 本会话强度是 MVP 攻坚期冲刺特例, 不可作为常态。** §10.2 「GM 执行核心」适合短期攻坚, 但若 M1→MVP 全程维持此强度, GM 单点是最大风险(RR-7)。**建议老雷在周报评估: P2 卫生项是否回流 IC, 释放 GM 写码带宽专注契约/风控/架构敏感路径。**

## 7. 给老雷的 5 条 takeaway

1. **流程图闭环跑通且抓到真 bug, spec+双签对契约/风控级改动 ROI 极高, 保留。** 但分层施加 (SOP-3), 单向安全改动免陪跑重流程。
2. **MVP 推进显著但未达 M1 demo 线**: 第一笔成交 60%、零风控失效 40%, 真实剩余阻塞是 **Goalserve 白名单(外部)** 不是代码。

4. **进周报升级 3 项: RR-1 Goalserve(即时P0)/RR-3 PnL bug(M2前)/RR-7 节奏单点(模式可持续性)。**
5. **5 条 SOP 固化**: CI grep 单位守护(已焊)/改 RM 必复签/改动分层/spec 误判亲验兜底/测试 stale 常量。
