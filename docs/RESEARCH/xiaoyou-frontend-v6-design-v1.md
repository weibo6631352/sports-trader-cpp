## 1. v5 现状体检 (小尤观察)

**布局:** 单屏一长列 — GlobalBar顶条 + PnlSparkline + EventGrid纵向堆叠 + SecondaryFooter折叠抽屉。数据都在一张页面, 切换成本为零, 但密度压力大。

**市场结构 (已认可, v6必须保留):**
```
Event (赛事)
  └─ Condition/盘口 (ConditionColumn)
       ├─ CondQuote  (AI量化: fair_value / edge / kelly / notional)
       ├─ DualBook   (双边订单簿: token0 YES + token1 NO, 各3档)
       └─ CondPos    (持仓 + per-market PnL)
```
这个三层结构是v5重要认可结果, v6保持不变。

**目前痛点 (体感评估):**

1. 观测信息散落 — 系统健康、WSS状态、p99延迟等挤在顶部一行, 信息过度压缩, 扫读需要额外解码
2. Prometheus裸文本在SecondaryFooter里折叠, 对开发人员极不友好 — 需要自己解析metric名称才能读懂
3. 订单簿深度只显示3档, 且无视觉深度条, imbalance只是一条细bar
4. PnL归因瀑布折叠在底部, 交易员盯盘时看不到
5. 无订阅市场数量、WSS每个topic的连接状态、reconnect次数等开发观测数据
6. 页面只有1个视图, 交易员和开发员的需求混在一起, 彼此都受干扰
7. SolidJS已引入但组件风格仍是手写CSS class系统, 没用组件库标准件

### 3.2 内容增强清单 (相比v5)

**订单簿深度 (当前v5只有3档):**
- 扩展到5档 (bids[0..4] + asks[0..4])
- 每档增加可视深度条 (相对最大量归一, 买单绿色条左对齐, 卖单红色条右对齐)
- imbalance进度条加数值标注 (当前只有细条没数字)
- WSS状态点从token级下移到half-book行内, 更明显

**量化字段 (当前v5已有但显示紧凑):**
- 置信度从数字变为条形+数字组合 (conf-bar: 0-100%, 颜色绿/黄/红)
- CI区间从小字tooltip改为直接显示在公允价下方 (一行)
- 信号强度 (signal_strength) 加视觉编码 (数值+方向箭头)

**赛事头部:**
- 数据延迟从全局迁到每个赛事组内 (staleness per-event)
- 进行中赛事加"实时"角标 (绿点+LIVE文字)

**筛选栏 (新增):**
- 全部 / 进行中 / 有持仓 三个快速filter
- 赛事文本搜索框 (本地filter, 不发请求)

**市场结构 (保持v5认可的结构不变):**
- Event→Condition→DualBook(token0+token1) 层级不变
- CondQuote+DualBook+CondPos三段式不变
- 仅在三段内部做内容加密

### 4.4 观测页 UX 纪律

- 状态灯配色: ●绿=正常 ●黄=降级/告警 ●红=故障 ○灰=未知/未连接
- 数值颜色: 延迟 <100ms绿, 100ms-1s黄, >1s红; 拒单数>0变红
- 不显示私钥/签名相关任何字段 (ADR-038 §5安全黑名单)
- Prometheus裸文本仍保留 (作为折叠抽屉兜底), 但主展示是结构化卡片
- 热力表staleness: 格子颜色随值变化, 不需要读数字就能扫到异常

## 6. 组件化建议

### 6.1 当前v5组件状态

v5用的是纯手写CSS class系统 (style.css 约500+行), 没有引入组件库。SolidJS已就位但只用了框架的响应性, 组件风格仍是自定义。

### 6.2 v6推荐引入的组件库

**建议: SUID (SolidJS版Material Design) 或 Kobalte (SolidJS无头组件库)**

从UX层面, 两条路都可行:

**路线A — SUID (MUI for SolidJS):**
- 优点: stat卡片/表格/tab组件开箱即用, 视觉统一
- 适合Ops观测页的stat panel风格
- 注意: bundle体积比Kobalte大

**路线B — Kobalte (无头组件) + 自定义样式:**
- 优点: 无头(behavior only), 保持现有深色终端风格
- Tabs/Select/Dialog/Toast等交互原语
- 体积小, 与现有style.css共存

**UX层面的建议 (给小苏参考, 不替小苏决策):**
- Tab导航 → Kobalte Tabs (无头) 或直接SolidJS signal控制, 避免引入重库
- Stat卡片 → 轻量自定义组件 (StatCard: label+value+颜色+单位), 无需MUI级别
- 数据表格 → 保持For循环渲染, 加thead/tbody语义
- 状态灯 → 统一StatusDot组件 (●绿/●黄/●红/○灰 + title tooltip), 替换当前分散的wss-dot-sm/acc-dot等
- Badge/Tag → 统一Badge组件 (替换当前的 badge/ gate-chip/ demo-chip/ mode-badge等10+种手写class)
- 深度条 → DepthBar组件 (size/maxSize props → width%), 复用在订单簿各档位

## 9. 信息密度控制

老板明确: "重功能/可读性/方便, 不重美观"。

密度控制原则:
1. 盯盘页: 每个ConditionColumn宽度保持, 增加档位纵向扩展, 不要横向再加列
2. Ops页: stat卡片网格2x4布局, 不要一行排8个; 卡片内留白, 数值字号够大
3. 颜色编码替代文字: 绿/黄/红状态灯减少阅读负担 (扫一眼不用读字)
4. 折叠/展开: Prometheus裸文本保留在Ops页折叠区, 不强制展示
5. 数值格式: 保持v5的mono-main/mono-sub层级, 重要数值大一号
