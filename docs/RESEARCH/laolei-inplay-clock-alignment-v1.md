# Goalserve inplay feed 时钟相位对齐 — 调研

> owner: 老雷 (GM) · last_review: 2026-06-04
> 触发: 老板「inplay 接口两秒一变,我们能不能纳 2.01s 的而不是 2.99s 的数据」

## 1. 问题

inplay odds feed 每 ~2s 出一版新数据。我们轮询若相位不对,会持着"快过期"的版本
(~2.99s 老)而非"刚出炉"的版本(~2.01s 老)。能否把轮询相位对齐到 feed 的更新时钟?

## 2. 实测

| 项 | 值 | 出处 |
|---|---|---|
| 轮询间隔 | `poll_interval_ms = min_fetch_interval_ms = 1005ms` | `app/paper_daemon.cpp:932-933`, `inplay_feed_thread.hpp:88-90` |
| 限速 | per-sport 1 req/s (非 per-IP 全局) | `inplay_feed_thread.cpp:544` |
| feed 更新间隔 (tennis, 18 版本) | 均 **2.08s** / 中 2.07 / min 2.05 / max 2.14, σ≈0.03 | 日志 updated_ts 序列 |
| 现 data_source_ts 新鲜度 | 1.2–2.9s 抖动 | 前序决策路径实测 |
| bet365→GS 中继 | P50 2.3s / P95 3.7s | [[gs-bet365-latency-2300ms]] |

feed 时钟极稳 (σ≈0.03) → 下一版时刻可高精度预测,相位对齐技术可行。

## 3. 延迟分解

总信号延迟 = 真实赔率变动 → 我们决策,分三段:

| 段 | 量级 | 可否动 |
|---|---|---|
| ① bet365→GS 中继 | ~2.3s | ✗ 改不了 (上游) |
| ② 版本年龄 (GS 每 2s 出版,任一时刻持有版本 0~2.08s 老) | 0~2.08s | ✗ 物理下限 (GS 出版频率) |
| ③ **轮询相位** (新版已就绪、我们持旧版未轮到) | 0~1.0s | ✓ **对齐可消** |

**对齐只消 ③**:均省 ~0.5s、最坏省 ~1.0s。总延迟 ~3.5–5.2s → ~3.5–4.2s。

## 4. 真正价值:稳,不是快

现新鲜度 1.2–2.9s 抖动,3s 门 (`sharp_max_staleness_sec=3.0`) 在倒霉相位上**误杀**本不该丢的
sharp 信号。对齐后稳定 ~2.1–2.3s → 门基本不再误触发。**这是对齐最实在的收益,不是"快 0.5s"。**

## 5. 算法 (轻量, ~30 行)

1. 已有 `last_updated_ts_ms_` per sport。加:收到新版的单调时刻 `R_v` + 间隔 EMA(初值 2.08)。
2. 下次轮询排到 `R_v + interval_ema + 0.15s margin`(新版落地后即取)。
3. 轮到却拿同一 `updated_ts`(太早/丢版)→ 退 0.3s 重试,守住 1005ms 地板不破限速。
4. 拿到新版 → 重锚 R_v + 更新 EMA。

落点: `inplay_feed_thread.cpp` token-bucket sleep 段 (line ~590-598)。

## 6. 成本 / 收益

- 成本: ~30 行改 sleep 调度,零新依赖。
- 限速: 1 poll/版 ≈ **0.48 req/s**,比现在 1 req/s **更省**,零超限风险。
- 收益: 削 ③ (~0.5s 均 / 1s 最坏) + 3s 门不再误杀 = 信号利用率↑。
- **不改结构性结论**: 滞后 sharp 仍打不过已 price-in 的活市场 (①②为延迟主项)。详 [[no-bet365-pm-convergence-edge]]。

## 7. 建议

**做。** 理由是便宜 + 让 3s 门不误杀,属卫生项;不是因为它能救 +200u(救不了)。
